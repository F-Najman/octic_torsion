# octic_torsion

This repository contains the code and logs for the computations in degree 8 of the paper
*Torsion of elliptic curves over number fields of degree 6, 7, 8 and 9* (F. Najman, 2026). The
statement numbers below are those of the version of November 2026 of that paper. The code and logs are
those of revision `41667ee`; later revisions change only this README. The computations in the other degrees are in
[sextic_torsion](https://github.com/F-Najman/sextic_torsion) (degree 6),
[septic_torsion](https://github.com/F-Najman/septic_torsion) (degree 7) and
[nonic-torsion](https://github.com/F-Najman/nonic-torsion) (degree 9). The code was first written for
a separate version of the proofs for degree 8; the files of that version, from which this repository
was built, are called the original record below.

In degree 8 the paper proves (Theorem 1.1)

  Φ(8) = Φ^∞(8) ∪ {Z/33, Z/34, Z/35, Z/39, Z/40, Z/42, Z/5 × Z/10, Z/3 × Z/15},

so that exactly 60 groups occur as the torsion subgroup of an elliptic curve over a number field
of degree 8 (the 52 groups of Φ^∞(8), determined by Najman and Varivoda, and 8 sporadic groups). It
also determines all elliptic curves over octic fields with a subgroup Z/33, Z/34, Z/35, Z/39, Z/40
or Z/3 × Z/15 (Theorem 1.2).

The table in [Which script proves what](#which-script-proves-what) is the authoritative map from
each statement of the paper that rests on a computation in this repository to the script that
verifies it and the log that script produced. In the digital version of the paper, the words
reporting a computation are links to the script that carries it out. The paper proves most
statements for several degrees at once, and in many places a computation in degree 9 (in
nonic-torsion) also covers degree 8. The octic computations that the paper uses only as checks, and
everything that Section 15 of the paper says about the computations of this repository, are in
[Further checks](#further-checks). Most logs can be regenerated with
[`verify_all.sh`](#reproducing-the-computations). Some cannot be regenerated by a single command,
because the run was interrupted, cut by a time limit, or continued by hand inside a Magma session;
they are marked "archived" in `jobs.txt`, and the section [Archive-only logs](#archive-only-logs)
explains each of them. Where such a log carried part of a proof of the original record, the
computation was repeated for this repository as one fail-closed batch run, and the new log is the
one cited below; see [Reruns made for this repository](#reruns-made-for-this-repository). All other
logs are those of the original runs, byte for byte; see
[Provenance of the committed logs](#provenance-of-the-committed-logs).

This repository is organized like [quintic-torsion](https://github.com/F-Najman/quintic-torsion)
(the computations for degree 5), sextic_torsion and septic_torsion, except that the octic
computations are about ten times larger, so the files are grouped in one folder per case.

## Getting the code

The Magma code depends on [mdmagma](https://github.com/koffie/mdmagma), which supplies the
moduli-theoretic routines (`MDX1`, `MDX11`, `HeckeOperator`, `DiamondOperator`, `ModuliPoint`,
`CuspOrbitsQ`) and, through its own `Magma` submodule, Sutherland's optimised models of
`X_1(N)` and `X_1(M,N)`. The point counts use Sutherland's
[GL2 package](https://github.com/AndrewVSutherland/Magma). Both are pinned as submodules, at the
same commits as in sextic_torsion and septic_torsion.

```bash
git clone https://github.com/F-Najman/octic_torsion
cd octic_torsion
git submodule update --init                       # mdmagma and gl2
git -C mdmagma submodule update --init Magma      # Sutherland's models, used by mdmagma
git -C mdmagma apply ../mdmagma-magma2.30.patch   # needed with Magma V2.30, see below
```

Do not use `git clone --recurse-submodules`: mdmagma has a further submodule
`tests/magma-unittest` registered under an SSH URL, so a full recursive clone can fail without a
GitHub SSH key. It is not used here.

The pinned commits are mdmagma `d1c019c6` (with its `Magma` submodule at `6a5a68a8`) and the GL2
package at `e70690a`. The latter two are different checkouts of the same repository on purpose:
mdmagma pins a commit that predates `gl2points.m`, so the point-count scripts attach the separate
copy in `gl2/`, and every other script attaches mdmagma's. The original record kept its own copy
of both packages; apart from Magma's signature caches (and a checkout of the unused
`tests/magma-unittest`), that copy agrees file by file with these commits plus the patch below.

**The mdmagma patch.** Magma V2.30 rejects two statements of the pinned mdmagma: an
`end intrinsic` without its semicolon in `v2/curves/divisors.m` and in
`v2/modular_curves/base_curve.m`. All computations here were run with a copy of mdmagma in which
these two semicolons had been added, and nothing else changed. `mdmagma-magma2.30.patch` makes
exactly this change; apply it with the command above. `verify_all.sh` checks whether it is
applied and applies it if not.

## Running the computations

All scripts are run from the repository root; the `Attach`, `AttachSpec`, `load` and `Read`
paths and the paths of the logs and data files are resolved from there. Everything was run with
Magma V2.30-1. The Python scripts need Python 3 with SymPy (`python3 -m pip install sympy`);
`independent/placecounts_pari.py` also needs `cypari2` (as in Sage), and `independent/fields8.py`
(and `independent/ranks8.py` without `--offline`) need `psycopg2` and network access to the LMFDB
mirror. The shell driver requires Bash 4.4 or later and GNU
command-line tools. Magma commands use `-n` to suppress personal startup files.

Several drivers take parameters, passed as `magma -n -b Name:=value script.m`:

* `common/hecke_sieve_smart.m` and `common/hecke_sieve_quotient.m` — the Hecke sieve on
  `X_1(N)`, with parameters `N`, `p`, `Qs`, `D`, `M`, `MemGB`, `Shard`, `NShard`, `FromDegree`,
  `MaxPart` (and `BaseNs`, the levels of the quotients, for the second). A run with `FromDegree` or
  `MaxPart` treats only the partition types of degree at least `FromDegree` and largest part at most
  `MaxPart`, and ends in `SIEVE_RESUME_DONE`.
* `common/generic_cartier_completion_export.m` — the local expansions of the Cartier test at 2
  on `X_1(N)`, with `TestN`, `D`, `MemGB` and `JetFile`, the file the expansions are exported to; the
  exhaustive rank tests are then replayed in Python by `common/replay_fi_jets.py` and
  `common/replay_cartier_projection.py`.
* `common/winding_probe.m` (`N`), `large_levels/finite_fields_2_octic.m` (`Ns`, `Ps`, `K`).
* a few drivers of single cases (`Shard`, `Limit`, `Tag`, `D`, `MatrixFile`, `JetFile`,
  `C420FullStem`, ...); see `jobs.txt`.

Everything else runs without parameters. The commands that produced the committed logs are in
`jobs.txt`. For example:

```bash
magma -n -b N:=44 p:=3 D:=8 M:=1 Qs:=5,7,13,17,19 MemGB:=4 common/hecke_sieve_smart.m
magma -n -b TestN:=45 D:=8 MemGB:=8 JetFile:=C45/data/N45_completion_jets.m common/generic_cartier_completion_export.m
python3 common/replay_fi_jets.py C45/data/N45_completion_jets.m
python3 common/candidates.py
```

Magma may buffer its output, so a terminated run can leave an empty or incomplete log, and some
Magma errors return exit status 0. Check both the exit status and the closing marker: every
script prints a marker when it finishes, and the third column of `jobs.txt` gives it for each
log. Many scripts end without `quit;`; run them with standard input at end of file
(`< /dev/null`), as `verify_all.sh` does, so that Magma exits when the script ends. A few original
runs were started without `-b` (their logs begin with Magma's banner and end with its `Total
time` line); their commands in `jobs.txt` omit `-b` as well, so that a rerun prints the same
frame. Scripts that write their log themselves (`SetLogFile`, or a file opened by the script)
are run with their standard output discarded (`> /dev/null`). Two Python drivers run Magma
themselves, through the `magma` on the `PATH`: `C2x30/reproduce_C2x30.py` and
`C4x20/reproduce_C420.py`.

## Reproducing the computations

`jobs.txt` lists each log file, the command that produces it, and its closing marker. An optional
fourth column gives an expected result as an extended regular expression.

```bash
./verify_all.sh                 # every job, Magma jobs one at a time
./verify_all.sh -j 4            # Magma jobs four at a time
./verify_all.sh C45/            # only the jobs whose log path contains C45/
./verify_all.sh -j 4 C2x        # both
python3 -m unittest discover -s tests   # the driver's tests and checks of the committed files
git diff                        # what the rerun changed
```

The tests check the driver and the committed files: the closing markers and expected results of
the committed logs, the files named in the commands and loaded by the scripts, and that every log
and data file kept byte for byte still has the SHA-256 recorded in the original proof ledger
(`common/data/evidence_sha256.tsv`). Run them on the committed tree, before rerunning jobs.

The driver overwrites the selected logs in place; `git diff` compares the new output with the
committed run. It runs the selected Magma jobs first, then the other jobs one at a time and in
the order of `jobs.txt`, because the Python jobs read the logs and data files written by the
Magma jobs. When Magma jobs are selected, the driver first applies the mdmagma patch if
necessary and then attaches every package once, in separate processes, so that parallel jobs do
not compile the same signature files at the same time.

Some scripts write further logs besides their standard output (a driver that runs several Magma
stages, a script with its own log file). Such a log is listed in `jobs.txt` with the command
`written by the job of LOG`; the driver checks it after the job of `LOG` has run, and selecting it
selects that job.

A job passes only if its command exits 0, its closing line is the expected marker (optionally
followed by a space and details), and any result expression matches. The closing line is the
last non-blank line of the log, ignoring carriage returns, a trailing `Script done on ...` line
written by `script(1)`, and trailing lines that consist of a CPU time only. The markers omit the
CPU times at the end of the closing lines. As Magma reports most errors on standard output,
carries on and exits with status 0, a job also fails if its log reports a Magma error. Some
drivers catch the errors of their stages and print a line containing `FAILED` instead; look for
such lines in `git diff` as well.

`jobs.txt` has 568 lines: 297 Magma jobs, 151 Python jobs, 45 logs written by
another job, and 75 archive-only logs. Rerunning all jobs costs about 43 hours of
CPU time, most of it on the longest computations listed under [Hardware](#hardware).

The jobs that export data rewrite the corresponding files in `data/`; a correct rerun rewrites
them with the same content, with the exceptions below. Some computations choose representatives in
an order that Magma does not fix (a representative of a diamond orbit, a curve in an isomorphism
class, the order of places, random points or test curves). A rerun can therefore print different
representatives and write the same records in a different order or with other random points.
Where later jobs refer to the committed order of such records, rerun an export only together with
the jobs that read it, or restore the committed file with `git checkout` before rerunning those
jobs. This concerns the point data of `C54/C54_good8_enumeration_v2.m`, read by the four `C54`
shards; the direct enumerations of `C2x36` and `C2x42`, whose record indices the later filters
use; the keys exported by `C4x20/preflight_4_20_D4_Aut96.m`, with which the later `C4x20` scripts
compare their own; and the arithmetic of `C3x18/sieve_3_18_D4_fullaut_root_v4.m`, which
`C3x18/replay_M3N18_root.py` compares with the committed diagonal data.

Some jobs share files, so with `-j` greater than 1 run the following one at a time (for
example `./verify_all.sh -j 1 C55/`), or rerun a job that failed because of them on its own:

* a few computations were run twice in the original record and both logs are kept; their two
  jobs run the same script and write the same export (the two jobs of
  `C55/C55_cartier_reproduce.m`, of `C65/C65_good6_D8.m`, `C65_good7_D8.m`, `C65_good8_D8.m`,
  `C65/winding65_hecke2_certificate.m`, `C4x16/M4N16_D4_final_RR13.m`,
  `C48/clean_run_v2/high_witness_replay_v3_shard0.m`, `C39/C4_dyadic_certificate_v2.m`, ...);
* `C2x42/C242_root_pair118_RR.m` reads the export of `C2x42/refine_C242_genus31_pair118_v2.m`,
  which a parallel rerun of the latter rewrites;
* the jobs of `C48/hecke_degree6_residuals_af_xy.m`, `..._degree7_...` and `..._degree8_...` fork
  four, two and two Magma processes, and the logs of the forked shards are checked as soon as the
  parent process ends, so a shard that is still writing its last line is reported as incomplete;
  check it again when it has finished.

`C75/C75_good7_certificate_root_v2.m` chooses points at random, and in one of our reruns an
assertion of `common/pair_af_place_linear.m` (that a chosen coordinate pair determines a single
place) failed; the next run passed. `C3x18/sieve_3_18_p13_postdiagonal_root.m` depends on the
order in which Magma lists places, which depends on the random seed; its command fixes the seed
(`-S 2`).

What a successful reproduction should change, and nothing else:

* timing figures, including the `time=...` fields, the `Time:` and `Total time` lines and the
  bare CPU times;
* Magma's banner and the paths in its `Loading "..."` lines, which name the original working
  directories, and the input paths and SHA-256 hashes that some replays print;
* the choice of representatives, random points and test curves, and the order of records,
  described above;
* whitespace, and whatever a different version of Magma prints differently, such as the printed
  form of a model or an ideal, the order of the elements in a printed set, or the verbose trace of
  a class-group computation.

Everything else is a genuine discrepancy: the place counts, the Hecke primes and cusp conditions,
every `RESULT`, `SURVIVOR` and `SUMMARY` line, the group invariants and class-membership results,
the dimensions and ranks of the Riemann–Roch and Cartier tests, and the closing markers.

### Archive-only logs

These logs are kept because they are part of the original record of the proof, but no single
command regenerates them. Each is listed in `jobs.txt` with the command `archived: ...`, and is
not rerun by `verify_all.sh`.

* `C46/logs/N46_p3_smart.log` and `C46/logs/N46_p3_single_completed.log` — the original Hecke sieve at 3 on `X_1(46)` (Codex Prop. 3.40), `N:=46 p:=3 D:=8 M:=1 Qs:=5,7,11,13,17,19 MemGB:=4 hecke_sieve_smart.m`. It completed the single-place types (4), (5), (6), (7), (8) (5, 4, 5, 24, 71 tests, all killed) and was stopped by hand after 26 of the 275 tests of the type (4,4), which were then done faster with the quotient filter (`C46/logs/N46_p3_mixed_quotient.log`). `N46_p3_single_completed.log` is the log the original proof cites: the first 282 lines of `N46_p3_smart.log` (up to `RESULT type=[ 8 ] total=71 survivors=0`), followed by the line `SINGLE_BRANCH_CHECKPOINT_DONE ...`, which Codex appended when it cut the log and which no script prints. `common/audit_quotient_combined.py 46` and `C46/audit46.py` read this cut log. The whole sieve was rerun to completion for this repository (`C46/logs/N46_p3_smart_rerun.log`), with the same command and `common/hecke_sieve_smart.m`; that rerun is the primary log for the single-place types. The paper does not use this computation: it proves the case n = 46 of Proposition 6.7 with nonic-torsion (see [Further checks](#further-checks)).
* `C51/logs/N51_prefix27_RR_control_root.log` — a control of the `X_1(51)` export (Proposition 7.9) by direct Riemann–Roch (`C51/N51_prefix27_RR_control_root.m`), run under `timeout 900`. Only the two completed kernels, written to `C51/data/N51_prefix27_RR_control_root_data.m`, are used: `common/compare_rr_to_completions.py` checks that they agree with the frozen export (`C51/logs/N51_full_RR_crosscheck_root.log`). `magma -n -b C51/N51_prefix27_RR_control_root.m` without a time limit computes all three kernels.

The export was rerun to completion for this repository, with the same command and `common/generic_cartier_completion_export.m` (`C49/logs/N49_completion_rerun.log`, all 27 cusps, with the replays of its jet file); that rerun is the primary log of this computation.

## Further checks

Section 15 of the paper describes the computations that its proofs do not need: runs in a smaller
degree that are covered by a computation in a larger degree, second checks, replays, and the
independent recomputations. This section contains everything that Section 15 says about the
computations of this repository, with their scripts and logs, and the other computations of this
repository that the paper no longer uses for its proofs (most of them proved a degree-8 case in the
separate version of the proofs for degree 8). For each check it names the statement checked and the
computation, here or in another repository, on which the paper's proof rests. Statement numbers are
those of the paper; "nonic-torsion", "septic_torsion" and "sextic_torsion" are the other
repositories, and paths in them are given relative to their roots.

### Software, hardware and CPU time

According to Section 15, the computations were performed in Magma V2.30-1, apart from some auxiliary
ones in Python (such as the lists of groups, the values of Abramovich's bound, the queries to the
LMFDB and the replays of data exported from Magma), on the Mordell server of the Department of
Mathematics, University of Zagreb, with an AMD EPYC 9175F CPU and 384 GB of RAM. They use mdmagma
for the moduli-theoretic operations, Sutherland's optimized models of `X_1(n)`, the
Derickx–Sutherland models of `X_1(m,n)`, the low degree points of van Hoeij and the LMFDB for the
analytic ranks of newforms, and the Hecke operators on closed points of `X_1(m,n)_{F_p}` were computed
with the routines of §10 of [N5] (the paper on degree 5), extended to m ≥ 3 by carrying both level
points through the isogenies. The computations in degree 8 took about 39 hours of CPU time in total; this figure does
not include the reruns made for this repository, which took about 15 hours, nor the independent
recomputations. In this repository Sutherland's GL2 package is also used, for the independent point
counts of `common/independent_counts.m` below (Section 15 mentions it for degree 6), and
`independent/placecounts_pari.py` uses PARI through cypari2. See also [Hardware](#hardware).

  rows of [Which script proves what](#which-script-proves-what) say where these counts are compared
  with the counts from the models.

#### Formal immersion at 2

The folder `independent/formal/` rechecks the Cartier (formal immersion) certificates at 2 with its
own models of the curves and its own code (`independent/formal/formal_common.m`). On `Y` over `F_2`
(or `F_q`), with `C` the Cartier operator and `U = (C − 1)H^0(Y, Ω^1)`, it checks for every
effective cuspidal divisor `B = Σ m_P P` of degree `d` that `dim U − dim(U ∩ Ω(−B)) = d`. It takes
one basis of `H^0(Ω^1)` (`DifferentialSpace(0)`) and the matrix of Magma's `Cartier`, after checking
`C(df) = 0` and `C(f^2 ω) = f C(ω)`; the spaces `{ω : v_P(ω) ≥ m}` at the cusps are computed as
Riemann–Roch spaces or from local expansions; all effective cuspidal divisors of degree `d` are
enumerated depth first, and their number is compared with `Π (1 − x^{deg P})^{−1}`. The expansion
method agrees with Riemann–Roch on all 103 kernel spaces of `X_1(63)/⟨8⟩` and on two spaces of
`X_1(49)`. As a known positive, on `X_1(25)` over `F_16` (which maps with degree 10 to
`X_0(25) ≅ P^1`) the pipeline finds 2798 rank failures among the 43758 reduced cuspidal divisors of
degree 10, and `h^0(D) = 2` was confirmed directly for five of them; so it detects genuine rank drops.
The models: `X_1(45)` from the Tate normal form of `X_1(9)` and a point of order 5; `X_1(63)/⟨8⟩`
from `X_1(9)` and a root of `ψ_7` (degree 24); `X_1(3,21)` over `F_4` from `X_1(7)` and two points of
order 3; `X_1(25)` over `F_16` and `X_1(49)` from the numerators of `x([5]Q)` and `x([7]Q)`. The
rechecks concern the degree-8 certificates of this repository; for Propositions 7.7 and 7.12 these are
checks in the paper (see above).

## Provenance of the committed logs

The computations were run in the working folders of the original record, with paths relative to
its root (`work/degree8/...`) or absolute. For this repository the files were moved into the
present layout and every path in the scripts was rewritten accordingly. Apart from paths, the
Magma scripts are identical to the versions that ran, with these exceptions:

* Magma's `Write` and `PrintFile` append to an existing file. So that a rerun replaces the
  exported data instead of appending to the committed copy, the first write to each exported file
  now has the option `Overwrite:=true` (or the script truncates the file first). The original runs
  wrote to new files, so this does not change their output.
* A few scripts were given a parameter in place of an environment variable or a hand-edited
  constant (noted below).

The Python audits and replays were adapted to the layout: they read and write the paths here.
Their checks of the SHA-256 hashes of scripts whose paths changed, and their reads of the proof
fragments, of copies of papers and of the original proof ledger, were removed, since the git
history and `common/data/evidence_sha256.tsv` now bind the files together. The logs are those of
the original runs, byte for byte (`common/data/evidence_sha256.tsv` records their SHA-256 in the
original ledger); the only new logs are those of the reruns described above. A rerun of an
adapted script can therefore print other paths or a shorter list of hashed files than its
committed log.

For this repository, every Python job and every Magma job whose recorded CPU time is under five
minutes (380 jobs, all but the `Z/48` Hecke job of degree 6, which forks four Magma
processes) was rerun in a copy of the repository, in addition to the reruns described above. All of them reproduced their committed logs up to the differences listed under
[Reproducing the computations](#reproducing-the-computations); the details are in the build notes.

Several computations were run twice in the original record, the second time by the reviewing
agent (the files called `..._root...` or `root_fresh_...`). Where the two logs are byte-identical,
one of them is kept; otherwise both are kept, each with its own job.

## Hardware

The computations were run on the server Mordell at the University of Zagreb, with an AMD EPYC
9175F CPU (16 cores, 32 threads) and 384 GB of RAM, using Magma V2.30-1. The committed runs of the
original record took about 39 hours of CPU time in total (the CPU times recorded in the logs,
counting interrupted runs up to the interruption; this is the figure that Section 15 of the paper
gives for degree 8), and the reruns made for this repository about 15 hours. The CPU times recorded
in the committed logs of the original record and of the independent recomputations in `independent/`
add up to about 49 hours.
The longest single computations were the complete Hecke sieve on `X_1(46)` (30067 s, the rerun
made for this repository; the original run had stopped after 8779 s), the export of the Cartier
expansions on `X_1(49)` (13614 s for the rerun, the original run was killed after 9725 s) and on
`X_1(51)` (13183 s), the octic tests on `X_1(40)` (four shards of about 7000 s each in the
original record, 7052 s for the whole fresh sequential run, including the proved class group), the
sieve at 3 on `X_1(44)` (5838 s), the Cartier export on `X_1(45)` (2280 s) and the quotient sieve on
`X_1(50)` (2055 s). The CPU times of forked processes (the `X_1(40)` shards, the `Z/48` Hecke
tests) include the time spent before the fork, so these totals are upper bounds. Runs were given
memory limits of 2–32 GB, and one of 128 GB.
